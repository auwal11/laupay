# Wallet & Ledger Model

This is the most safety-critical document in the project. Every engineer
touching money-moving code must read this first.

## 1. The Core Rule

> **A wallet's balance is never written directly. It is only ever changed by
> inserting an immutable ledger entry inside a database transaction.**

There is no code path anywhere in this system that does:

```ts
wallet.balance = wallet.balance - amount   // FORBIDDEN
```

Instead, every balance change is expressed as a `LedgerEntry` row, and the
wallet's `balance` column is a cached, transactionally-consistent projection
that is updated **in the same DB transaction** as the ledger insert.

## 2. Entities

### `WalletAccount`
One per user (or per agent-role user). Holds:
- `id`, `ownerId`, `ownerType` (`USER` | `AGENT`)
- `balance` (cached — see rule above)
- `currency` (`NGN` for now)
- `status` (`ACTIVE`, `FROZEN`, `CLOSED`)
- `version` (optimistic lock, incremented on every balance change)

### `LedgerEntry` (append-only, never updated, never deleted)
- `id`
- `walletAccountId`
- `direction` (`CREDIT` | `DEBIT`)
- `amount` (always positive; direction determines sign)
- `balanceAfter` (snapshot, for auditability and fast reconciliation)
- `reason` (`ORDER_PAYMENT`, `WALLET_FUNDING`, `AGENT_CASH_COLLECTION`,
  `REVERSAL`, `ADMIN_ADJUSTMENT`, ...)
- `referenceType` / `referenceId` (polymorphic link to the Order/Payment/etc.
  that caused this entry)
- `idempotencyKey` (**unique** — see below)
- `createdAt`

### `WalletTransaction` (optional grouping wrapper)
Some operations produce more than one ledger entry (e.g. a reversal produces
a compensating entry rather than deleting the original). `WalletTransaction`
groups related entries for a single logical business event, mainly for
reporting; `LedgerEntry` remains the actual source of truth.

## 3. Idempotency

Every ledger-affecting request (an order payment, a webhook, an admin
adjustment) must carry an **idempotency key** that is:

- generated by the caller for client-initiated actions (e.g. "pay for this
  order" — the order ID itself can serve as the natural key), or
- derived deterministically from the provider event ID for webhooks (e.g.
  `payment_event:{provider}:{providerEventId}`).

`LedgerEntry.idempotencyKey` has a **unique constraint**. The ledger service's
`credit()`/`debit()` primitives always do a "insert-or-return-existing"
operation: if a ledger entry with the same idempotency key already exists,
the existing result is returned and **no second entry is written** — this is
what makes retries, duplicate webhooks, and double-taps on "Pay" safe.

## 4. Atomicity & Concurrency

- Every balance mutation happens inside a single `SERIALIZABLE`-safe DB
  transaction that:
  1. Locks the `WalletAccount` row (`SELECT ... FOR UPDATE`) — this is the
     row-level locking required by the project brief.
  2. Re-reads the current balance under the lock.
  3. Validates the operation (sufficient balance for a debit; wallet not
     frozen; amount is positive; etc.) using the just-read value — never a
     value read earlier or supplied by the client.
  4. Inserts the `LedgerEntry`.
  5. Updates `WalletAccount.balance` and increments `WalletAccount.version`.
  6. Commits.
- If any step fails, the whole transaction rolls back — there is never a
  partial state where a ledger entry exists but the balance wasn't updated,
  or vice versa.

## 5. Negative Balance Prevention

A `DEBIT` ledger primitive re-validates `balanceAfter >= 0` **inside** the
locked transaction immediately before insert. This is enforced at two layers:
1. Application logic (the check described above).
2. A database `CHECK` constraint on `WalletAccount.balance >= 0` as a last
   line of defense against any future code path that forgets step 1.

## 6. Reversals

Ledger entries are **never deleted or edited**. To reverse a transaction
(failed order after a debit, chargeback, admin correction), the system
inserts a new, opposite-direction `LedgerEntry` with `reason: REVERSAL` and a
`referenceId` pointing back at the original entry/order. The full history —
original debit and its reversal — remains visible in the ledger forever.

## 7. Why balance is cached at all

Summing all ledger entries on every read would be correct but slow at scale.
Because every write to `WalletAccount.balance` happens in the same
transaction as the ledger insert that justifies it, the cached balance is
always exactly equal to `SUM(ledger entries)` — this invariant is checked by
a reconciliation job (`docs/architecture/payment-flow.md §6`) and by the
integration tests in `backend/test/wallet.e2e-spec.ts`.

## 8. What Agents Do Differently

An agent's `WalletAccount` behaves identically to a customer's for ledger
purposes. The difference is upstream: when an agent collects cash from a
walk-in customer and confirms it in the app, that confirmation creates a
`Payment` of type `AGENT_CASH_COLLECTION`, which — once confirmed — credits
the *order/service cost* against the **agent's own wallet** (debiting it, as
the agent is "spending" their float to fulfil the customer's order) or, in a
prepaid-float model, debits the agent's float wallet directly. The specific
settlement model (agent floats down as they sell vs. agent is credited
commission after) is a product decision to be finalized before Phase 2 — see
`docs/decisions/0002-agent-settlement-model.md` (open).
